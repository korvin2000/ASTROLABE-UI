# Почему простые задачи занимают 40+ ходов и что с этим сделано

Разбор трёх живых сессий из `diags/` (2026-10-01, ядро после D-357…D-362) и правки по его итогам.
Продолжение `harness-fiasco-analysis.md`. Проверено по событиям (`journal.call`, `journal.result`,
`cell.gate_fired`, `cell.model_responded`) и по коду ядра и Studio.

## 0. Вердикт

1. **Проект не надо бросать, и «графы и chunks» — не причина.** Во всех трёх сессиях граф был тривиальным: один
   increment, plan-ячейка пропущена (D-360 работает). Ходы уходили не на граф, а на три другие вещи: harness не умел
   запустить `npm`, инструменты отказывали там, где намерение модели однозначно, и «ритуал» (регистр STATE, гейты,
   выход) требовал от модели формальностей, которые не приближают к цели.
2. **30–47 % ходов содержали отклонённый вызов**, 6–12 ходов за сессию потеряны полностью. Это не глупость моделей:
   в рассуждениях обе модели правильно ставили диагноз за 3–4 хода (циклический импорт найден на 4-м ходу, через
   40 секунд), а дальше боролись с harness.
3. **Главный единичный дефект — запуск команд на Windows.** `run ["npm","test"]` → `CreateProcessW failed (2)`:
   `npm` — это `npm.cmd`, а запуск без shell не смотрит в `PATHEXT`. Отсюда «на машине нет npm» (20 ходов
   самодельной загрузки Angular из tarball'ов), отсюда же «приёмка недоступна» у самого harness и вечный `blocked`.
   Вывод прошлой сессии «npm в системе нет» (fiasco §9) был неверным по той же причине.
4. **Вторая причина — время, а не ходы.** Каждый штамп дерева перечитывал и хэшировал все файлы, включая
   неотслеживаемый `devtools/` (461 МБ): 20–70 с до и после каждой правки, 100 с на открытие задачи. В сессии
   «исправь env.ts» модель думала 273 с, а harness и инструменты работали 1242 с.
5. **Claude Code быстрее не потому, что модели умнее**, а потому что у него: shell; 6 простых прощающих
   инструментов; чтение файла целиком; свободный todo без доказательств; никакой приёмки внутри цикла. ASTROLABE
   сильнее на границе (контракт, приёмка командой, квитанции), но те же строгие правила применял и *внутри* цикла,
   где они только тормозят. Оптимальный путь: строгость оставить на выходе, внутренний цикл сделать прощающим.

## 2. Механизмы

### X1. `run` не запускает `.cmd`/`.bat` по имени (Windows)
- `os/WindowsOwner.kt` `renderCommandLine`: обёртка `cmd /d /s /c` только если `argv[0]` буквально кончается на
  `.bat`/`.cmd`. `npm`, `npx`, `ng`, `mvn`, `gradlew` — shim'ы, которые находит только `PATHEXT`.
- `W-laq` ход 4: `npm -v` → unavailable → «no npm (CreateProcessW failed)» → ходы 5–23 — скрипт, качающий Angular
  из реестра вручную. Пользователь дважды вмешался («npm доступен, с чего ты решил…»).
- `W-i2k` ходы 10–15: шесть ходов поиска способа запустить `npm test` (`npm.cmd`, `where`, кавычки, `cmd /c`).
- `W-r2k`: приёмку `npm test` harness запускает тем же путём → `unavailable (runner missing)` → завершение
  отклонено → `budget.attempts 2 spent` → `blocked_external`, хотя `cmd /c npm test` у модели проходил 34/34.
  Модель в ответ правила `gradlew.bat` и предлагала поправку контракта — лечила harness, а не задачу.

### X2. Штамп дерева перехэширует всё
- `workspace/Stamper.kt` `report()`: `stampEntry` для каждого неотслеживаемого файла и `captureEntry` для каждого
  отслеживаемого — чтение и SHA-256 при каждом вызове; ячейка штампует несколько раз за ход.
- `C:\temp\play3`: `devtools/` не в `.gitignore`, 1018 файлов, 461 МБ. `git status` — 0,06 с, штамп — десятки секунд.
  Перед каждой правкой 70 с (`journal.call → cell.tool_called family=edit`), открытие задачи 100 с.
- Побочно: эти же файлы раздувают счётчик `files=1131` → форма S1, размер L.
- Уточнение после замеров: при тёплом файловом кэше ОС сам штамп на этом дереве стоит ~2 с, shadow-снимок — 6,5 с
  (после D-364 — 2 с и 0 прочитанных файлов). 70-секундные паузы из живой сессии офлайн не воспроизведены
  (холодный кэш и конкуренция за диск с запущенными сборками); в прогонах после правок накладные расходы harness
  вместе с командами — около 3 с на ход.

### X3. `look`
- Чтение целого файла больше 1500 токенов (~150 строк) — отказ с оглавлением вместо первой страницы
  (`look/Look.kt`, ветка `LookTarget.Whole`). Каждый файл крупнее — лишний ход.
- Аргумент `range` для `read` игнорируется (нужно `target: "path:a-b"`): `W-r2k` ходы 13–17 — пять отказов подряд
  на одном файле. `recall` с `id: "14"` вместо `#14` — шесть отказов в одном ходе (`W-laq` ход 19).

### X4. `edit`
- `expect` на верхнем уровне вместо внутри op → ошибка схемы, весь ход потерян (3 раза у GLM).
- `delete` + `create` одного пути в одном пакете → отказ; пакет на 15 КБ модель пересылала четыре раза
  (60+ с генерации каждый), в итоге удаление прошло без создания.

### X5. `state` (регистр)
- Лимит патча 400 токенов — 7 отказов; `anchor.version` требует 64 hex; `evidence: "#35 #36 #37"`; лишний ключ.
- Из-за отклонённых патчей STATE устаревает, и выход отклоняется: «шаг плана без disposition» (см. X6).

### X6. Гейты и бюджет
- **Stall** считает прогрессом только изменения регистра: срабатывал на 3-м ходу каждой задачи и каждые 3 хода
  при реальной работе («36 turns without progress» при написанном Angular-приложении). Модель: «the stall flag is
  spurious» — гейт обесценен.
- **Impact**: удаление временного файла, созданного самой ячейкой → «`env` removed; 426 references not inspected»,
  до 10 предупреждений за ход (совпадения по голому имени), и они же блокируют выход.
- **Reserve**: с 32-го хода из 40 правки запрещены. `W-laq`: дерево сломано предыдущим пакетом, восемь ходов
  подряд модель пытается создать один файл и получает отказ; ячейка кончается, auto-политика принимает «done».
- **Exit**: шаги плана без отметки блокируют завершение, даже когда приёмка зелёная.

### X7. Промпт
- Нет фактов о хосте: ОС, как работает `run`, какие инструменты есть в PATH. Модель выясняет это отказами.
- Нет правила про язык ответа: DeepSeek написал итог русскоязычному пользователю по-китайски.
- 14 правил kernel + таблица ошибок на внутреннем жаргоне (KNOWN, anchor, `[>]`, packet) — много внимания
  уходит на протокол.

### X8. Завершение и продолжение
- Сообщение пользователя во время работы поднимает версию контракта; если оно пришло после последнего хода,
  предложение завершения «привязано к v3, контракт уже v4» → отказ → списана попытка (`budget.attempts`).
- Studio на «Продолжить» возобновляет ту же кампанию, а ядро попытки не восполняет: три запуска подряд по
  12 секунд с тем же `blocked`. Задача мертва.

### X9. Recap отравляет следующий запуск
- В follow-up Studio кладёт итог прошлого (неудачного) запуска как «Summary»: «run заблокирован маской окружения».
  GLM на 12-м ходу: «The contract says: run is masked… I violated the rule» — и сдалась, хотя команды работали.

### Что не подтвердилось
- «Модель концентрируется на графах»: графа не было. Концентрируется она на STATE и отказах: 8 из 39 ходов
  `W-i2k` — только патчи регистра или их повторы.
- «Не пользуются памятью»: проектной памяти у задач Studio фактически нет — файл правил (`AGENTS.md`,
  `.astrolabe/rules.md`) ядро умеет, но Studio его не привязывает; реплика «сохрани, что java в devtools» стала
  поправкой контракта одной задачи и в следующую не попала.

- 9 раз модель присылала `state` с лишней `}` в хвосте JSON — каждый раз ошибка схемы и повтор (остальные вызовы
  хода при этом уже исполнялись — D-372 сработал);

- три команды отклонены политикой (проба `if exist` вне проекта, `rmdir` внутри проекта), и модель сделала то же
  через `node -e`;
- impact-предупреждения на CSS и Markdown (`}` — «498 ссылок»).

### 4.1 Прогон на второй модели: `z-ai/glm-5.3-flash` (финальный код до третьего раунда ревью)

Запрос «напиши todo (REST)»: за 163 с и 17 ходов модель написала приложение и прогнала свой smoke-тест; **1
отклонённый вызов на 17 ходов (5 %)**, ни одного срабатывания гейтов. На 17-м ходу провайдер прислал вызов
инструмента с пустым `id`, и транспортный SDK бросил `Tool call id must not be blank` — запуск завершился `failed`
(209 тыс. токенов). Это дефект SDK, не harness: запасной id подставлялся только при отсутствующем поле, а не при
пустой строке. Исправлено в `llm-transport-sdk` (ветка `fix/blank-tool-call-id`): пустой id → `call_<позиция>` во
всех кодеках и в потоковом накопителе; пустое имя инструмента → `unknown` вместо исключения; 248 тестов SDK зелёные.
Повтор прогона с исправленным SDK не выполнен: система разрешений запросила явное согласие владельца на повторный

## 5. Что дальше (в порядке эффекта)

1. **Регистр STATE — главный оставшийся налог.** В обоих прогонах ~25–30 % ходов касались только заметок или их
   повторов. Следующий шаг — «прямой» профиль ячейки для S0/простого S1: заметки необязательны, план и факты
   harness выводит сам из квитанций (запуски, правки), короткий kernel, компактные схемы. Приёмка на выходе остаётся.
2. **Приёмка без команды** («The change fulfils the request» + auto-политика) делает результат «не проверено» и
   толкает модель на самодельные проверки. Когда модель сама создала и прогнала тест, его команду стоит предложить
   как приёмку (карточка «сделать `npm test` проверкой проекта»).
3. Авто-принятие непроверенной и незавершённой работы в режиме auto (решение D-337/D-340) — оставлено как есть;
   после ремонта резерва сломанное дерево менее вероятно, но политика по-прежнему примет «не закончено».
4. Резерв компиляции контекста не масштабируется под маленькие окна (16K): таким профилям нужны меньшие значения.
5. Неотслеживаемые тяжёлые каталоги (`devtools/`) по-прежнему попадают в атлас и в выбор формы (files=1131 → S1);
   стоит предлагать добавить их в `.gitignore` или исключать бинарные файлы из атласа.
6. Измерения в репозитории (R1 из `FABLE_ANALYZE_AND_IDEAS.md`): доля ходов «только STATE», «гейт сработал →
   привело к изменению», сценарный прогон ×3 как скрипт.
