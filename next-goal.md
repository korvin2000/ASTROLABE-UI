## 1. Что сломано (коротко)

За тестовый день 9 живых задач дали 207 обращений к модели и 1,53 млн токенов; завершились 2 из 9, обе на OpenRouter. На ChatGPT-подписке (`openai-codex/gpt-6-luna`, `gpt-6-astra`) не завершилась ни одна из 7.

1. **Review pass падает на `openai-codex`.** 18 из 18 вызовов закончились `FAILED` без единого токена вывода; на OpenRouter такие же вызовы проходят. Причина не установлена: текст ошибки нигде не сохраняется.
2. **Нет вердикта → тупик.** Критерий приёмки «The change fulfils the request» вправе оценить только review pass. Если он не дал вердикт, ядро отказывает в завершении, агент уходит в `blocked`, кнопка Continue запускает ту же ячейку заново.
3. **Согласие пользователя не закрывает задачу.** Сообщение «проверил, всё хорошо» записывается как поправка к контракту.
4. **Review pass не различает «плохо» и «не могу проверить».** Всё, что не `approve`, превращается в `Revise`.
5. **Один и тот же кандидат проверяется повторно** при каждом предложении завершения и после каждого Continue (tetris: 7 вызовов на одно дерево).
6. **Ядро блокирует и проваливает задачу при нехватке свидетельств:** недоступный раннер → `blocked` (`cell/Cell.kt:1045-1056`); второй отказ в завершении → `failed` (`cell/CellContext.kt:227-236`, `campaign/Lifecycle.kt:320-340`); нет квитанции или оценки на финише → `failed` (`campaign/Controller.kt:1744-1746`).
7. **Текст Studio подменяет цель пользователя.** Заметки хоста дописываются в контракт как запросы пользователя, а «текущая цель» контракта — это последний запрос (`contract/Contract.kt:273-274`). Дайджест контракта в каждом ходе показывает модели заметку Studio вместо слов пользователя.
8. **Прошлая сессия гоняла живые приёмочные сценарии только на OpenRouter** (`ASTROUI/docs/progress.md:42`; там же S-3: «на ChatGPT-входе не проверено»). Поэтому сбой Luna не был замечен.

## 2. Правило владельца (главное требование фазы)

У проверки результата три исхода, и только один из них означает «не выполнено».

| Исход | Когда | Что делает система |
|---|---|---|
| **Принято** | проверка реально выполнена и одобрила | задача выполнена |
| **Отклонено** | проверка реально выполнена и нашла конкретные проблемы: упавший тест либо замечание с файлом, местом и сутью | задача не выполнена; агент получает замечания и исправляет |
| **Не проверено** | проверку нельзя выполнить, она неполная, чего-то не хватает, проверяющий упал, ответил неразборчиво или сам сказал «не могу проверить» | **никогда не «не выполнено»**: спросить пользователя в UI либо считать задачу выполненной с ярлыком |

Инварианты — каждый должен быть закреплён тестом:

- **I1.** Задача никогда не получает `blocked`, `failed` или «не выполнено» только потому, что проверка недоступна, неполна или ей чего-то не хватает.
- **I2.** «Не выполнено» возникает только из трёх источников: вердикт проверки с содержательными замечаниями; реально запущенная и упавшая проверка (красные тесты); явное «не выполнено» от пользователя.
- **I3.** Один и тот же кандидат при том же контракте и тех же критериях не проверяется повторно. Результат проверки хранится и переиспользуется, включая результат «не проверено».
- **I4.** Круг «замечания → исправление → повторная проверка» конечен: один круг исправления в ячейке (`cell/CellContext.kt:227-236`, `maxFinalizations = 2`), затем решает пользователь. Автоматического перезапуска нет.
- **I5.** Ожидание решения пользователя и его ответ «задача выполнена» не стоят ни одного обращения к модели: ячейка не перезапускается.
- **I6.** Любая остановка, связанная с проверкой, показывает пользователю причину и даёт выбор: «задача выполнена» или «не выполнена, доработать».
- **I7.** Происхождение приёмки записано в ядре по каждому пункту: проверено тестами, проверено review, принято пользователем, принято политикой без проверки. Непроверенное не выдаётся за проверенное.

Поведение по режимам (умолчания; владелец может изменить, см. §12):

| Режим задачи | Исход «не проверено» |
|---|---|
| `ask` | кампания останавливается в ожидании решения; в UI карточка с двумя кнопками |
| `auto` | принять от имени политики с ярлыком «не проверено: причина»; в карточке результата остаётся действие «не выполнена — доработать» |

### 4.2 Причина сбоя review pass на `openai-codex`

Факты:
- Ячейка работает: `AiGateAdapter` вызывает `llm.start(...)` — потоковый запрос с опциями профиля: `responseCache(BYPASS)`, `strict(true)`, уровень рассуждения, теги (`ASTROLABE/provider-ai-gate/.../ProfileBinding.kt:153-167`).
- `ReviewPass` вызывает `llm.complete(model, conversation)` без опций, без инструментов (`ReviewPass.java:98-99`).
- Квалификация профиля (`AiGateProfiles.qualify`) на том же провайдере тоже упала.
- Латентность сбоев 1,4–25 с, `first_output_ms` пуст. Это само по себе не говорит, на каком этапе произошёл сбой.
- В SDK путь есть и покрыт тестом на заглушке: `Engine.complete` читает SSE-ответ как поток (`Engine.java:230-255`), `CodexWireTest.completeStreamsTheCodexDialectAndCollectsTheEvents`. Оба пути используют один и тот же разбор SSE.
- Кэш ответов в Studio не настроен (`TransportService.java:131-139`), так что он причиной быть не должен.

Причина не установлена; ошибка в SDK не доказана. Гипотезы — в порядке проверки:
- **H2.** Backend отклоняет форму запроса: нет инструментов, нет уровня рассуждения, нет `sessionId` при `sessionHeaders(true)`, собственный `instructions`.
- **H3.** Клиентский дедлайн или политика повторов по умолчанию у `complete()`.
- **H1.** Ошибка SDK при сборке результата потокового ответа внутри непотокового `complete()`: финальное событие без текста, ответ только с рассуждением.

Сначала зафиксировать факты — класс исключения, HTTP-статус, `content-type`, последние события потока — и только потом называть причину.

Эксперименты на уровне SDK, модель `openai-codex/gpt-6-luna`, по одному отличию за раз:

| # | Вызов | Что покажет |
|---|---|---|
| E1 | `complete(model, "Reply with OK.")` без опций | воспроизведение |
| E2 | `complete` с теми же опциями, что у ячейки (`ProfileBinding.options`) | проходит → причина в опциях: H2 |
| E3 | `stream(...)` / `start(...)` с тем же разговором без опций | проходит → причина в пути `complete`: H1 или H3 |
| E4 | `complete` + `reasoning(LOW)` | H2 |
| E5 | `complete` + `sessionId` | H2 |
| E6 | `complete` с system + user в форме review pass | H2: `instructions` |
| E7 | `complete` с одним фиктивным инструментом | H2: запрос без инструментов |

Для каждого записать: исход, класс исключения, `LlmException.code()`, `httpStatus()`, `providerCode()`, сообщение, усечённое тело ошибки без токенов. Проще всего — временный параметризованный тест рядом с `LiveSmokeTest` (там идентификатор модели `gpt-5.5` зашит; нужен `gpt-6-luna`).

## 5. Часть A. Ядро: правило приёмки (репозиторий ASTROLABE) — высший приоритет

### Модель

Сейчас ядро знает два ответа на предложение завершения: принято и отказано. Отказ при нехватке свидетельств ведёт к `blocked` или `failed`. Новая модель разделяет три вещи.

- **Обязательство** — то, что должно быть подтверждено: пункт приёмки increment'а либо обязательство уровня кампании (полный suite, review кампании, регрессионная перепроверка, quality gate). У каждого устойчивый идентификатор.
- **Результат проверки** — факт о кандидате: `passed`, `failed` или `unverified` с причиной. Источники — квитанции проверок и вердикты проверяющего. Хранится и для того же кандидата, определения обязательства и входов не получается заново.
- **Решение о приёмке** — слово полномочного лица о том, что делать с непроверенным или отклонённым review: `accept` (кто, почему) или `rework` (кто, текст). Хранится отдельно от результатов, привязано к кандидату и версии контракта. Решение сильнее результата review, но не сильнее упавшей обязательной проверки.

**Разрешение** выводится из результатов и решений и имеет три значения:

| Разрешение | Когда | Что происходит |
|---|---|---|
| `complete` | каждое обязательство `passed` либо принято решением | приёмка фиксируется; по каждому пункту записано, проверен он или принят |
| `rework` | есть `failed`, не перекрытое решением, либо решение `rework` | агент получает замечания и исправляет |
| `await` | остались `unverified` без решения | кампания ждёт решения; не блокируется и не проваливается |

Результат проверки по обязательству. Сначала применимость свидетельства, потом его исход:

| Обязательство | `passed` | `failed` | `unverified` |
|---|---|---|---|
| `run:` и проверки кампании | квитанция актуальна, допустима и зелёная (`Currency.certifies`) | квитанция **актуальна и допустима**, исход `Failed` | всё остальное: нет квитанции, устарела, недопустима, `Timeout`, `InfraError`, `Inconclusive`, `NotRun`, `Unavailable`, `Denied`, `UnknownOutcome` |
| `check:`, `review:` | одобряющий вердикт проверяющего | неодобряющий вердикт хотя бы с одним замечанием уровня `Blocker` или `Major` | нет вердикта, `InsufficientEvidence`, неодобряющий вердикт без содержательных замечаний |

Два уточнения к нынешнему коду:
- `Currency.red` сейчас истинно и для устаревшей упавшей квитанции (`verify/Scheduler.kt:359`). Устаревшая квитанция — это `unverified`, а не `failed`.
- `Timeout` — `unverified`: проверка не завершилась. Сейчас `ReviewReceipt.failedRequired` считает его провалом (`delegate/EvidencePacket.kt:30`).

Недостающее одобрение флага test-integrity — тоже `unverified` с решением хоста, а не отказ (`verify/ExitGate.kt:111-115`).

### A1. Единый разрешитель приёмки

- **Сейчас:** правило завершения записано дважды и на строках: гейт ячейки (`cell/Gates.kt:326-341`, `cell/CellContext.kt:222-236`) и проверка контроллера (`verify/ExitGate.kt:51-118`, `Verifier`, `:173-229`) возвращают `missing: List<String>`. По строкам нельзя отличить упавшую проверку от отсутствующей; на них же построены подсказки модели и причины остановки.
- **Нужно:** один компонент, которым пользуются гейт ячейки, контроллер, финальная приёмка и возобновление. На входе — обязательства, результаты проверок, решения, регистр. На выходе — разрешение (`complete`, `rework`, `await`) и типизированные пробелы: вид (`failed`, `unverified`, прочее), идентификатор обязательства, текст. «Прочее» — незакрытый шаг плана, несовпадение версии контракта или stamp, неразрешённый impact nudge.
- **Где:** `verify/ExitGate.kt`, `cell/Gates.kt`, `cell/CellContext.kt`, `cell/Cell.kt:583-602`, `campaign/Controller.kt:1648-1667, 1707-1767`, `campaign/Lifecycle.kt:315-344`.
- **Тест:** `ExitGateTest`, `AcceptanceEvidenceTest`, `GatesTest` — по случаю на каждую клетку обеих таблиц; ячейка и контроллер дают одно разрешение на одних входах.

### A2. Решение о приёмке — отдельный вызов полномочия

- **Сейчас:** у полномочия один вызов для проверки, `Authority.review` (`event/Authority.kt:90-99`), и ядро делает его только для пунктов `check:` и `review:` (`campaign/Controller.kt:1480-1490`). Для `run:` без зелёной квитанции пути нет: гейт отказывает, недоступный раннер блокирует ячейку (`cell/Cell.kt:584, 1045-1056`).
- **Нужно:**
  - `review` остаётся вызовом **проверки**: проверяющий возвращает одобрение, отклонение с замечаниями либо `InsufficientEvidence`. Его ответ — результат проверки, не решение.
  - Новый вызов полномочия — **решение о приёмке**. Запрос перечисляет обязательства, по которым нужно решение: непроверенные (с причиной: «раннер не найден: python3», «таймаут 600 с», «проверяющий не смог оценить: …») и отклонённые review (с замечаниями), плюс ссылки на дифф, квитанции и итог агента. Ответ: `accept` (кто, почему), `rework` (кто, текст) либо `null` — решения сейчас нет.
  - Упавшая обязательная проверка в запрос решения не входит и решением не перекрывается — правило §8.8 остаётся.
  - У вызова есть Java-форма, как у остальных (`event/Authorities.kt`); `AutonomousAuthority` отвечает `null`.
  - Блокировка по недоступному раннеру (FX-13) удаляется: это частный случай `unverified`.
- **Тест:** кампания с недоступным раннером и решением `accept` завершается; красный тест решением не перекрывается; `rework` с текстом ведёт к доработке.

### A3. Нет решения — ждать, а не блокировать и не проваливать

- **Сейчас:** `null` от `authority.review` → «no assessment recorded» → ячейка продолжает ходы → второй отказ → `CompletionStalled` → `failed`.
- **Нужно:** при разрешении `await`:
  - ячейка заканчивается сразу: работа сделана, решение принимается вне ячейки. Ходов больше нет; это не отказ в завершении и не `partial`;
  - предложение завершения сохраняется долговечной записью **ожидающего завершения**: базовый и итоговый stamp, хеш патча, окружение, версия регистра, флаги test-integrity, пробелы, идентичность свидетельств. Сейчас пакет ячейки пишется в журнал одной строкой-сводкой (`cell/Cell.kt:1013-1022`), а контрольная точка предложения не содержит (`cell/Checkpoints.kt:26-41`) — восстановить его после остановки не из чего;
  - кампания останавливается `waiting_for_input` с **машинно-читаемым кодом остановки**, а не только со строкой причины. Нужны как минимум два кода: «нужно решение о приёмке» и «отклонено проверкой» (A5). Код доходит до хоста через слушатель запуска и чтения состояния;
  - исход ячейки для калибровки маршрутизатора выводится из разрешения: сейчас любая `Completed` записывается как принятая (`campaign/Controller.kt:1313-1317`).
- **Тест:** кампания с полномочием, отвечающим `null`, заканчивается `waiting_for_input` с кодом «нужно решение о приёмке»; после первого предложения завершения обращений к модели нет; `blocked` и `failed` не возникают; запись ожидающего завершения переживает закрытие хранилища.

### A4. Возобновление без ячейки (I5)

- **Сейчас:** возобновление всегда запускает новую ячейку (`campaign/Controller.kt:1192-1233`); вопрос ядра «May inc-1 resume?» задаётся до неё (`:666-683`).
- **Нужно:** один путь возобновления для S0 и S1 — после сверки открытых эффектов, до запуска ячейки и до проверок бюджета. Фиксация приёмки требует фазы `Running`: порядок `Resumed → Reconciled → Committed` (`campaign/Lifecycle.kt:248-258, 299-305`); последняя ячейка increment'а должна быть `Completed`, increment — в работе (`graph/RequirementGraph.kt:199-211`).
- Если есть ожидающее завершение и оно ещё действительно — stamp дерева, версия контракта и окружение те же, полномочие на публикацию не отозвано (`c.refusal()`), — запросить решение и повторить разрешение по сохранённой записи:

| Решение при возобновлении | Что делает ядро | Обращений к модели |
|---|---|---:|
| `accept` | фиксирует приёмку, завершает кампанию | 0 |
| `rework` с текстом | запускает ячейку-продолжение; текст приходит ей блоком замечаний (A5) | работа продолжается |
| решения нет | снова `waiting_for_input` | 0 |

- Если дерево, контракт или окружение изменились с момента остановки, ожидающее завершение недействительно: решение к нему не применяется, запускается ячейка.
- Решение `rework` действует на один запуск продолжения. Если после него кандидат не изменился, снова запрашивается решение, а не возвращается прежний отказ.
- Окна сбоя (остановка между записью ожидающего завершения и остановкой кампании, между решением и фиксацией) сверяются при открытии, до повторного применения.
- **Тест:** `ResumeTest`, `LifecycleTest`: остановка → `accept` → `completed` без единого запроса к модели; остановка → ручная правка файла → возобновление запускает ячейку; остановка → `null` → `null` — ноль запросов; сбой между решением и фиксацией не даёт двойной фиксации.

### A5. Замечания доходят до агента; проверенное не перепроверяется

- **Сейчас:** при неодобряющем вердикте работающая ячейка видит только «AC-1 … no assessment recorded» (`verify/ExitGate.kt:77-88`). Замечания попадают в регистр лишь следующей ячейки. `ReviewCell.obtain` переиспользует только одобрения, причём запись без списка версий файлов «актуальной» не считается никогда (`delegate/ReviewCell.kt:99-104, 153-161`) — поэтому неизменный кандидат проверяется заново.
- **Нужно:**
  - замечания и текст решения `rework` приходят ячейке **отдельным закреплённым блоком контекста** с указанием автора — так же, как закрепляются ответы на вопросы (`cell/Cell.kt:630-633`). Полный текст хранится долговечно. Через строку подсказки передавать нельзя: в неё попадают две детали по 240 символов (`MAX_NUDGES = 2`, `DETAILS_IN_LINE = 2`). Записывать в регистр работающей ячейки тоже нельзя: `steer` возвращает копию без новой версии, сохранение перезапишет существующую версию и обойдёт валидатор и предел размера (`register/RegisterVersions.kt:35-41`, `tool/state/StateTool.kt`);
  - результаты проверок всех трёх видов хранятся с ключом «кандидат, определение обязательства, входы» и переиспользуются. Для неизменного кандидата ни проверка, ни проверяющий повторно не запускаются — в том числе при возобновлении и в том числе для результата `unverified`;
  - решения хранятся отдельно и всегда сильнее сохранённого результата review: сохранённое отклонение не мешает спросить решение и принять его;
  - предел кругов прежний: первый отказ — ячейка исправляет и предлагает завершение снова; второй заканчивает ячейку. Если причина — отклонение review, кампания останавливается `waiting_for_input` с кодом «отклонено проверкой», а не `failed`: решает пользователь — продолжить исправление или принять как есть. Ячейка при этом заканчивается так же, как при `await` (A3), с сохранённым ожидающим завершением: иначе решение `accept` не сможет зафиксировать приёмку без новой ячейки. Упавшие тесты по-прежнему дают `failed`.
- **Тест:** `ReviewCellTest`: вердикт с тремя замечаниями → все три в контексте той же ячейки; повторное предложение без изменения дерева не вызывает проверяющего; пустой дифф тоже не перепроверяется; после второго отказа — остановка с кодом «отклонено проверкой»; `accept` при возобновлении завершает кампанию.

### A6. Происхождение приёмки по каждому пункту (I7)

- **Сейчас:** принятый increment целиком становится `Verified` (`verify/ExitGate.kt:217-222`, `contract/Contract.kt:42-47, 340`); квитанция знает статус пункта и общий список `notVerified` (`campaign/FinishReceipt.kt`), но принятое решением от проверенного не отличает.
- **Нужно:** происхождение выводит ядро из записей, а не хост полем в ответе: пункт с результатом `passed` — проверен; пункт, закрытый решением `accept`, — принят, с подписавшим и причиной. Различие видно в ledger требований, в квитанции завершения (`accepted` отдельно от зелёного, строка в `notVerified`), в представлениях для хоста (`event/Views.kt`) и в событиях. Кампания при этом `completed`.
- Публикация выше стадии `patch` требует проверенной приёмки; принятое без проверки — только `patch` (умолчание, §12).
- **Тест:** квитанции кампаний, принятых пользователем и политикой, различаются подписью и причиной; смешанный случай — один пункт проверен тестами, другой принят — записан попунктно.

### A7. То же правило на уровне кампании

- **Сейчас:** вне приёмки increment'а нехватка свидетельств тоже останавливает: обязательный review в S2 недоступен → `blocked_external` (`campaign/Controller.kt:833`); финальный полный suite не сертифицирован → `blocked_external` (`:1716-1719`); review кампании или снимок поведения для рефакторинга недоступны → `blocked_external` (`:1749-1758`); регрессионная перепроверка (`:955-974`).
- **Нужно:** провести эти обязательства через тот же разрешитель с теми же тремя исходами. Перепроверка неизменного кандидата не запускает уже выполненные проверки повторно.
- Эти пути вживую не наблюдались ни разу (все задачи Studio идут в S0). Закрепить фикстурными тестами: `CampaignLoopTest`, `S2CampaignTest`, `RefactorCampaignTest`, `ControllerTest`. Если изменение оказывается шире перечисленных мест вызова — остановиться и сообщить.

### A8. Исход `answered` для запроса без изменений — независимое изменение

- **Сейчас:** «ответил на вопрос» в ядре не существует: приветствие проходит приёмку как изменение кода.
- **Нужно:** новый исход кампании `answered` со своим переходом; `completed` и его инварианты (квитанции, ledger) не ослаблять.
- Условий два, и нужны оба:
  1. **явное заявление модели**: завершающая операция «запрос не требует изменений, вот ответ». Одного отсутствия изменений мало: иначе задача на реализацию, где агент просто остановился, превратится в «ответ» и молча потеряет свои обязательства;
  2. **проверка фактов ядром**: stamp дерева равен stamp исходного снимка, эффектов классов W и D не записано. Если факты не сходятся, операция отклоняется.
- Применимость решается до запуска проверок при остановке (`cell/Cell.kt:519-526`); ячейка и контроллер пользуются одним правилом.
- Завершение без явного заявления идёт через обычную приёмку.
- **Тест:** заявление без правок → `answered`, полномочие не спрашивается; заявление после правки отклонено; остановка без заявления и без правок → обычная приёмка, не `answered`.

### A9. Контекст хоста вместо поправок от имени пользователя — независимое изменение

- **Сейчас:** единственный способ дополнить контракт — `Contracts.amendByUser` (`contract/Contracts.kt:129-136`). Studio дописывает им инструкции, и они становятся «текущей целью» (`contract/Contract.kt:273-274`), попадают в дайджест контракта и закрепляются как слова пользователя.
- **Нужно:**
  - инструкции хоста идут отдельным каналом контекста хоста и помечены как заметки хоста; поправками контракта они не являются;
  - структурные изменения контракта от хоста (добавить пункт приёмки, задать защищённые пути) вносятся поправкой с автором-хостом, без текста в списке запросов пользователя;
  - цель контракта и закреплённые запросы остаются дословными словами пользователя.
- Затронуты проверка покрытия закреплённого текста и дайджест (`context/Compiler.kt`, `register/ContractDigest.kt`, `context/Precompile.kt`); для уже сохранённых запросов определить автора по умолчанию.
- **Тест:** `ContractsTest`, `CompilerTest`, `PrecompileTest`: после заметки хоста цель контракта — по-прежнему запрос пользователя; префикс контекста между ходами стабилен.

## 6. Часть B. Studio поверх ядра (репозиторий UI)

После части A Studio не обходит ядро, а отвечает на два его вызова и показывает его состояния. Оба вызова проходят через `AuthorityPort` (`backend/bridge/.../HostApi.kt:69-77`) и `PortAuthority` (`HostAuthority.kt`); вызов решения о приёмке в них нужно добавить.

### B1. Проверка: три ответа review pass

- **Сейчас:** `ReviewPass.java:105-133` — всё, что не `approve`, становится `Revise`; при пустых замечаниях синтезируется `Major`.
- **Нужно:** review pass — только проверяющий. Он честно возвращает ядру результат и политикой не занимается. Вердикт модели — `approve | revise | cannot_verify`. Черновик системного текста:

```text
astrolabe-studio · review pass
You check one finished change against the user's request. You see the request, what the user said during the
task, and the change as a diff. You cannot run anything and you see no other files.
Answer with exactly one verdict:
- "approve": the change does what was asked and you see no defect in the shown change.
- "revise": you found a concrete defect IN THE SHOWN CHANGE that breaks what was asked. Every finding names the
  file and line and says what is wrong. Missing information is never a defect.
- "cannot_verify": you cannot tell, because something you would need is not visible to you: program output,
  other files, a running application, an action that leaves no trace in files, the environment. Say what is missing.
Judge only what the diff shows. Do not demand tests or proof of actions such as opening a browser.
If the request needed no change to the files and nothing was changed, that is "approve".
Between "revise" and "cannot_verify" choose "cannot_verify".
Reply with one JSON object and nothing else:
{"verdict":"approve"|"revise"|"cannot_verify","summary":"one sentence",
 "findings":[{"severity":"blocker"|"major"|"minor","location":"path:line","issue":"what is wrong"}],
 "missing":"what could not be checked"}
```

| Ответ проверяющей модели | Что уходит в ядро |
|---|---|
| `approve` | одобряющий вердикт, подпись `studio:review-pass(<model>)` |
| `revise` и есть замечание `blocker` или `major` с непустыми `location` и `issue` | неодобряющий вердикт с замечаниями |
| `revise` только с `minor` | одобряющий вердикт; замечания показать пользователю как заметки |
| `revise` без пригодных замечаний; `cannot_verify` | `InsufficientEvidence` с названным недостающим |
| неразборчивый ответ; исключение; таймаут | `null`; причина записана (B6) |
| `approve`, но дифф был усечён или свидетельство прочитано не полностью | `InsufficientEvidence`: «проверена часть изменений» |

- **Тест:** таблица ответов → вердикт. `FixtureBrain` уже узнаёт `REVIEW_MARKER` (`FixtureBrain.kt:69`): научить демо-модель отдавать каждый вариант по ключевому слову запроса.

### B2. Решение о приёмке: политика по режимам

- **Сейчас:** `DecisionService.review` (`DecisionService.java:174-182`) отдаёт ядру результат review pass как есть; до пользователя запрос не доходит ни в `ask`, ни в `auto`.
- **Нужно** — ответ на новый вызов решения (A2):
  - `auto`: `accept` от имени политики, с причиной из запроса. Отклонённое review политика не принимает: отвечает `null`, задача останавливается как не выполненная.
  - `ask`: если есть сохранённое решение пользователя для этого кандидата и версии контракта — вернуть его; иначе `null` сразу.
- При `null` кампания заканчивается в ожидании (A3). Подвешенного ожидания в Studio нет, перезапуск backend ничего не теряет. Проект не считается занятым: другая задача в нём может стартовать. Аренда рабочей области остаётся за тем же владельцем и переиспользуется при возобновлении.
- Известное ограничение: если, пока задача ждёт решения, дерево проекта изменится (другая задача, ручная правка), ожидающее завершение устареет и возобновление запустит ячейку (A4).

### B3. Карточка решения и ответы

- **Сейчас:** карточки знают три вида — `question | approval | suggestion` (`DecisionService.cardOf`, `:460-493`; `core/model.ts:39-53`; `features/task/cards.ts:16-66`); пауза показывает одно действие Continue (`error-actions.ts`). Состояние задачи выводится разбором строки причины (`TaskService.stateOf`, `:126-176`; `failureCode`, `:179-184`).
- **Нужно:** состояние задачи и карточка выводятся из кода остановки ядра (A3, A5).

| Код остановки | Карточка | Кнопки |
|---|---|---|
| нужно решение о приёмке | «Результат не удалось проверить автоматически: <причина>. Задача выполнена?» | **«Да, выполнена»** · **«Нет, доработать»** |

## 12. Решения, принятые по умолчанию (владелец может изменить до старта)

| Вопрос | Умолчание |
|---|---|
| Исход «не проверено» в режиме `auto` | принять от имени политики с ярлыком; альтернатива — всегда спрашивать |
| Отклонено review в режиме `auto` | политика не принимает; задача останавливается как не выполненная, решает пользователь |
| `Timeout` проверки | «не проверено», а не «отклонено» |
| Может ли пользователь принять результат, отклонённый проверяющей моделью | да: его решение сильнее результата review |
| Может ли пользователь принять результат при упавших тестах | нет; для этого нужно менять контракт — вне объёма |
| Разрешает ли принятие без проверки публикацию | только стадию `patch`; стадии выше требуют проверенной приёмки |
| Сколько действует решение «доработать» | один запуск продолжения; если кандидат после него не изменился, решение запрашивается снова |
| Что разрешает исход `answered` | явное заявление модели плюс проверка фактов ядром; несогласный пользователь отвечает сообщением |
| Предел кругов исправления по замечаниям | один круг в ячейке (`maxFinalizations = 2`); не менять |
| Модель для review pass | та же, что у задачи; отдельная дешёвая модель — фаза 3 |
| Пропуск review для мелких изменений | не делать в фазе 0 (это триггеры по риску, фаза 3) |
| Коммиты | UI и SDK — только по просьбе; ядро — локальные по его `CLAUDE.md`; пуш — никогда без просьбы |
| A8, A9 и часть E | после живой приёмки частей A–D; при нехватке времени перенести, записав |
