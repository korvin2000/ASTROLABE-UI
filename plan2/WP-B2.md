## Часть B2a (t3) — runner + `interrupt-csv` + `env-launcher` + `wrong/` для v0
1. **`wrong/` в самопроверке:** `eval-live check` и `TaskValidityTest` проверяют для каждой задачи: приёмка падает на
   базе; падает на база+`wrong/`; проходит на база+`reference/`; видимые тесты зелёные на эталоне (как сейчас).
   Задача без `wrong/` — ошибка загрузки.
2. **Скрытое вне дистрибутива:** в установленном `bench/<tag>/` нет открытых `acceptance/`, `reference/`, `wrong/`
   (сейчас они лежат в `tasks/<id>/` и читаемы агентом через `run`). Безопасный вариант по умолчанию: упаковать их
   ресурсами в jar внутри `lib/` и читать через classloader; открытыми остаются `task.json`, `prompt.md`, `base/`.
   Исходное дерево `eval-live/tasks/` не меняется. Тест: загрузчик задач получает скрытые части из ресурса; README.
3. **Утечка пути через окружение:** выяснить, наследуют ли процессы агента (`run`) окружение процесса runner'а
   (`APP_HOME`, `EVAL_LIVE_OPTS`, `JAVA_OPTS`, `CLASSPATH` из стартового скрипта); если да — не передавать их
   (средствами runner'а или скрипта, ядро не трогать). Тест или запись в отчёт с доказательством.
4. **Сценарий `interrupt`:** после K-го `cell.model_responded` runner отменяет попытку
   (`campaign.cancellation.cancel(...)`), дожидается исхода, затем делает то, что делает Studio на сообщение
   пользователя после остановки: `amend` контракта текстом ограничения + продолжение/повторный запуск в той же задаче
   (образец: `C:\work.astrolab\ASTROUI\backend\server\src\main\java\io\astrolabe\studio\tasks\TaskService.java`
   ~640–700, `continueRun`). Если агент закончил раньше K — то же как follow-up в той же задаче. `result.json`:
   `interrupt` {на каком ответе, режим `cancelResume|followUp`, исходы обоих отрезков}; totals — сумма отрезков.
   Тест на поддельном провайдере. Если без правки публичного API ядра нельзя — остановиться, описать (критерий отказа).
5. `wrong/` для трёх v0: `bugfix-pagination` — чинит только случай из `repro.py`, граничный (пустой/ровно полный)
   остаётся сломан; `api-currency` — меняет API, но один вызывающий остаётся на старой форме; `rest-todo` — нет одного
   метода/кода ответа, который проверяет smoke (например, 404 на отсутствующий id).
6. **`interrupt-csv`:** модуль отчётов; запрос — «добавь экспорт недельного отчёта в CSV: `export_weekly(report, path)`,
   строка заголовка, даты ISO». `interrupt` K = 3, ограничение: «Новое требование: разделитель `;`, публичную
   `export_rows` не менять». Приёмка: `;`, заголовок, ISO-даты, сигнатура `export_rows` прежняя. `wrong/` — запятая
   (позднее ограничение потеряно). Эталон — `;`.
7. **`env-launcher`:** `dev.py test` (запуск `unittest` подпроцессом) вызывает интерпретатор по имени `python3` из
   `PATH` и всегда выходит с кодом 0. Запрос: «`python dev.py test` на этой машине не работает; почини лаунчер, чтобы
   он работал на любой ОС, и чтобы падение тестов давало ненулевой код». Приёмка запускает `{python} dev.py test` с
   `PATH`, где нет ни `python3`, ни `python` (работает только `sys.executable`), на зелёных и на намеренно красных
   тестах (код ≠ 0). `wrong/` — `python3` → `python`. Эталон — `sys.executable` + код возврата.
8. README: формат (`wrong/`, `interrupt`), упаковка, `check`.

## Часть B2b (t2) — `red-test`, `ui-clear-done`, `investigate-totals`
Своя ветка от `main`; runner не трогать. Валидность проверить существующим `eval-live check` (база/эталон) и
вручную для `wrong/` (команды и вывод — в отчёт); после слияния оркестратор прогонит общий `check`.
1. **`red-test`:** небольшой склад (`inventory/`); на базе красный видимый тест
   `tests/test_reorder.py` (дозаказ, когда остаток **≤** порога; код использует `<`). Два пути кода: одиночная позиция
   и пакетный пересчёт `reorder_batch`; видимый тест покрывает только одиночный. Запрос: «CI красный: падает
   test_reorder; тест верный, его не менять; почини код». Приёмка: своя копия теста + скрытые случаи пакетного пути и
   границы; байты `tests/test_reorder.py` рабочей области равны базе. `wrong/` — исправлен только одиночный путь.
2. **`ui-clear-done`:** todo-приложение: `server.py` (`http.server`, `/api/todos` GET/POST/PATCH) + `static/index.html`
   + `static/app.js` (vanilla JS), без сборки. Запрос: кнопка «Clear completed» (`id="clear-completed"`) удаляет все
   выполненные; скрыта, если выполненных нет; счётчик «N items left» обновляется. Серверная часть — новая операция
   (например, `DELETE /api/todos?done=true`). Приёмка: поднимает сервер на свободном порту, проверяет API (удаляются
   только выполненные), разбирает HTML (`html.parser`) — кнопка есть; `app.js` вызывает эту операцию и вешает
   обработчик на кнопку (статическая проверка текста). `wrong/` — сервер удаляет **все** задачи. Видимые тесты API
   зелёные на базе и эталоне.
3. **`investigate-totals`:** счета: загрузчик → нормализатор → агрегатор → форматтер; `repro.py` показывает неверный
   итог за месяц — расхождение ровно на сумму счёта с отметкой времени ровно в полночь 1-го числа (он попадает в оба
   месяца: конец интервала включён). Запрос пользователя подсказывает ложную гипотезу: «похоже, ошибка округления
   float». `wrong/` — переход на `Decimal`/другое округление без исправления границы (приёмка падает). Эталон —
   полуоткрытый интервал `[начало, начало следующего)`. Приёмка: скрытые случаи на границах месяцев (в т.ч. високосный
   февраль, полночь), суммы не меняются от смены округления.
