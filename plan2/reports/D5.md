## Решение (Fable 5.1, оркестратор; D-445)
1. **Протокол по умолчанию для всех классов моделей остаётся `structured`; direct — выбираемая опция** (Studio `protocol = auto` →
   `structured` для каждого класса). Основание: на deepseek direct **доказанно не хуже** structured по запросам (0,77 [0,57; 1,06]),
   некэшированному входу (0,79 [0,60; 1,04]) и времени (1,01 [0,56; 1,79]), пол качества №9a соблюдён (15/16 против 15/16), но
   денежная ось **не доказана**: парное D/S 0,865 [0,61; 1,22] по счёту (точечная экономия 9–13 %), ни один ценовой профиль не
   доказывает выигрыш ≥ 20 % (только MiMo без скидки на кэш доказывает «дешевле»: 0,66 [0,46; 0,94]). Мощность screening для
   эффекта 20 % — 22 %. Исход «не доказано» — допустимый по §9.3; базовая политика остаётся.
2. **glm-5.3-flash: не измеримо.** Прогоны ядра испорчены апстримом InferenceNet (D-444); после исключения осталась одна чистая пара
   (`bugfix-pagination` r2: D/S 0,59). Чистый glm-screening — первая закупка (`wd2`, 48 прогонов).
3. **Ранжированный список потерь direct против `loop`** (deepseek, разрыв D−L; №29 — что оптимизировать в direct, а не повод заменить ядро):
   1. **Выход и прежде всего рассуждения**: лишний reasoning 96 тыс. токенов = 92 % лишнего выхода; по счёту deepseek выход объясняет
      ≈ 86 % денежного разрыва. Источник — объём рассуждений модели под протоколом ядра (3,3× против loop); причина не разобрана (S4 §2.4 п. 5).
   2. **Некэшированный вход на запрос 4,1×** (3 286 против 793): 73 % разрыва всего входа; из него ≈ 43 % — размер контекста на запрос
      (8,5 тыс. против 4,6 тыс.), ≈ 57 % — доля промахов кэша (доля кэша 61 % против 83 %; D−L −14,4 п.п. [−28,6; −0,2]).
      При ценах выход/вход ≈ 2–3 (MiMo, Qwen, Grok) вход — главная статья (55–67 % разрыва), при 5 (Fable) вход и выход сопоставимы.
   3. **Постоянная часть первого запроса 4,8×** (4 339 против 902 токенов: kernel + схемы + [S]) — сама по себе 5 % разрыва
      некэшированного входа, но она повторяется в каждом запросе как база контекста.
   4. **Число запросов уже меньше** (198 против 222) — не причина проигрыша.
   Задачи-концентраторы разрыва: `api-currency` (74 % разрыва), `interrupt-csv` (33 %); direct выигрывает у loop на `investigate-totals`, `ui-clear-done`.
4. **Вопрос владельца о линейном росте контекста `loop`.** На screening и на `scenario-1004` переполнения у `loop` нет (пик 13–16,5 тыс.),
   последний вход = пику (сжатия нет), наклон роста 300–400 ток/запрос — того же порядка, что у ядра; разница в константе
   (0,9–1,1 тыс. против 4,3–5,2 тыс.) и в доле кэша. На `scenario-1004` loop в 10× дешевле structured и в 10–20× — direct (1 из 2 прогонов
   direct не принят). **Точка пересечения не измерена**; условная модель (линейный рост loop против плоского контекста ядра с большей
   константой) даёт N* ≈ 300–560 запросов по счёту deepseek, ≈ 110–120 (MiMo), ≈ 240–480 (Qwen/Grok), ≈ 470–750 (Fable) при равном
   числе запросов; при наблюдаемом отношении запросов ядро/loop (1,6–2,9) — вдвое дальше. Плато ядра не измерено (наклон direct на
   длинной задаче 598 ток/запрос — больше loop), поэтому пересечение может и не наступить без оптимизации direct. Вывод: **дешевизна
   loop на средних задачах — измеренный факт; её исчезновение на длинных — пока гипотеза**, которую проверяет пилот из `D5-STATISTICS.md`
   («Чего данные не доказывают»): два семейства задач × три длины (≈ 100/300/600 запросов) × D/L ×2 = 24 прогона.
5. **Что докупить** (по убыванию пользы на доллар, из статистики): чистый glm-screening (48); завершить длинную страту deepseek (22);
   пилот точки пересечения (24–36); абляции direct на `api-currency`/`interrupt-csv` (16 на абляцию: постоянный префикс, кэш, reasoning);
   confirmation 24 свежих задач × 2 × D/S (96; мощность 82 % для эффекта 20 % против нуля, но доказать «≥ 20 %» при наблюдаемом 0,865 не удастся).
