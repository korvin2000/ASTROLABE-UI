## Решения
(черновые, без номеров: вопрос → выбор → почему → безопасная альтернатива)
1. **Где живёт `task.propose` для S1.** → одна роль `Roles.direct` на S0 и S1, 23 операции; в S0 операцию скрывает маска
   формы, как у структурной роли. Почему: набор схем выбирает роль (инв. 12), условие формы остаётся только в `mainLine` и
   масках; H2 сможет открыть `propose` в S0 как сигнал повышения, не меняя байтов `[S]` и схем. Цена: в S0 одна
   замаскированная операция в `[S]`/схеме (оценка +60–90 токенов кэшируемого префикса, +4 токена в `[A]`).
   Альтернатива: отдельная роль для S1 (S0 остаётся на 22).
2. **Вариант S2/S3.** → отдельная роль `Roles.directLead` (`direct-lead`), kernel `kernel-direct-lead/1`; текст kernel
   выбирается по маске роли (`task.delegate`), без нового поля `Role`. Альтернатива: поле `Role.kernel`.
3. **Виды делегирования.** → `task.delegate` только `kind=probe`. Почему: writer-ов диспетчеризует контроллер
   (`S3Run.kt:398-410`), у делегатора главной линии нет мест для writer (`Controller.kt:2258`, `ChildCells.kt:61`);
   ревью — одним путём, через `verify(review)`. Альтернатива: оставить `review` видом делегирования.
4. **`verify.review` из direct.** → открыт в lead, скрыт в `direct` и writer. Почему: в S2+ правило выхода может требовать
   ревью (`Judge.kt:55-71`); запрос до `finish` даёт доработку в той же линии, одобрение переиспользуется
   (`Verify.kt:240`). Альтернатива: скрыть, ревью только от контроллера после завершения ячейки.
5. **Правило №7 для S2/S3.** → `kb`, `look.impact`, `look.bmap` скрыты во всех direct-ролях. Почему: в волне H нет
   куратора и продвижения KB; lead получает impact/bmap/kb через структурный probe (`Role.kt:118`); собственная работа
   harness с impact от маски не зависит. Обратимо сменой маски одной роли. Альтернатива: открыть lead `look.impact`.
6. **Direct-writer.** → `Roles.directWriter` = `direct` без `task.propose` (22), kernel `kernel-direct/1`; выбор —
   `Roles.writerLine(protocol)`.
7. **Handoff direct-writer.** → внутри одной диспетчеризации: то же рабочее дерево, тот же handle, пакет и база; только по
   давлению; лимит — резерв токенов пакета (инв. 10) и `WriterBudget.handoffs = 2`, не из grant кампании; между эпохами
   ничего не объединяется, `Integrator` берёт один результат на handle; итоговый пакет строится на всю диспетчеризацию
   (чистые изменения от её базы, флаги целостности сохраняются). Исчерпание → failed writer, как сейчас.
   Альтернатива: без handoff у writer (любой partial — возврат главной линии).
8. **Аргумент формы.** → `contract.shape` на старте ячейки (его же читают маска хода и проводка делегирования), не
   `ShapeDecision` кампании. До H1 `mainLine(Direct, S2|S3)` возвращает `Roles.implementing`.
9. **Handoff по бюджету ходов.** → условие «цикл S0»: `runS0` сообщает ячейке, что своего продолжения у цикла нет.
   Семантика Dp2 сохранена, ячейка форму не читает.
10. **Причина handoff** типизирована: `HandoffCause { Pressure, TurnBudget }`, поле `CellExit.Partial.handoffCause`,
    далее `returned_handoff` → запись расхода (`cause`). Счётчик H2 «второй handoff по давлению в инкременте» читается
    из журнала без переделки D3.
11. **Тексты ворот G5, G8** в direct не называют операций, зависящих от формы (`task.propose`) — ворота форму не читают.
12. **`propose(kind=amendment)`** в direct не предлагается (поправка — `note(amend)`); совет «no tool call» после
    записанного плана (`TaskTool.kt:190`) в direct опускается.
13. **Строки A-D.7** H1–H4, D1 переименованы в E1–E4, K1.
