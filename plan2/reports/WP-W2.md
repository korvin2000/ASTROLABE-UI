# WP-W2 — стоимость захвата и снимка; нечитаемый файл не роняет прогон

Ветка `v2/W2` от `main` `79337a0` (после слияния W0). Исполнитель: суб-агент (Opus), worktree ядра.

## Сделано

  (открытие → ячейка правка/verify/done → переоткрытие → открытие второй работы `W-2` на том же хранилище) на 300 и на
  1500 файлах, по одному разу на класс; стражи WF-2 (процессы git каждого открытия и каждого снимка равны при 300 и 1500;
  захват читает файл не более одного раза: `filesRead + blobsRead ≤ файлы дерева (+ строки атласа на открытии) + 20`,
  20-МБ файл — один раз) и WF-3 (снимки после правки одного файла пишут ровно 1 объект; открытие новой работы пишет
  0 объектов и не публикует ни одного recovery-блоба, кроме своего нового манифеста). `UnreadableFileScenarioTest` —
  WF-4 (вариант `LockedFile`: исход — возобновляемая остановка с путём, run не бросает). На `main` все четыре стража
  красные (см. «Тесты»).

- **WD-01** (`ShadowRef.commit`): объекты записей, уже проиндексированных предыдущим снимком этой ссылки, берутся из его
  дерева по дайджесту (манифест называет дайджест, дерево — объект; в пределах экземпляра — из памяти, без `ls-tree`);
  остальные проверяются одним `git cat-file --batch-check`, и только отсутствующие пишутся одним
  `git hash-object -w --no-filters --stdin-paths` по файлам recovery-блобов. Каждый записанный id сверяется с id, который
  обязаны иметь сырые байты (§4.3, I-12; теперь и для SHA-256-репозиториев). Сигнатуры вызовов из `Controller.kt` не
  менялись.
- **WD-02** (одно чтение за захват): `ContentCache.Reads` — чтения одной операции захвата (наблюдение до чтения +
  содержимое); `DirtyState.capture` читает файл один раз, кладёт байты в хранилище под дайджестом этого же чтения

  контрольная перепроверка D-274 берут те же байты; перечитывается только файл, чьё наблюдение изменилось. Попытки D-274
  делят одно `Reads`. Git-id объекта считается из того же чтения (`DirtyState.objectId`), так что снимок не перечитывает
  блобы (`BlobStore.get`) ради `hash-object`. Свежие границы остаются свежими: свежий захват читает каждый файл с диска.
- **Повторная публикация** (п. 4): `BlobStore.put(bytes, digest, …)` не пишет файл и не открывает транзакцию строки,
  если блоб уже есть; объекты, которые git уже хранит, не пишутся (WF-3: новая работа — 0 объектов).
- **WD-05**: `Workspace.bytes` различает «нет файла» (`null`) и «файл есть, но не читается»: 3 попытки (50 и 100 мс),
  затем `UnreadableInput(path, attempts)` (публичный, `IOException`, путь относительный). Захват/штамп его не глотают —
  нечитаемый файл никогда не выпадает из идентичности. Ячейка отвечает на него `CellExit.Blocked` с путём (вместо
  `Failed`, как в R2 «packet failed … IOException») → `blocked_external`, возобновляемо.
- **Дополнение по ревью W0** (замечания оркестратора): (1) атлас запускает `git ls-files` через git живого

  новых полях `phase.counted` `blobsRead`/`blobBytesRead` (`ShadowRef`, `DirtyState.bytesOf`); (3) фикстура

  `Workspace` корня находится через слабый реестр `liveWorkspace(root)` (Controller передаёт атласу только путь).
- **Байты штампа и манифеста не изменились**: `CaptureBytesTest` закрепляет значения, посчитанные старым кодом

## Решения
- Как снимку узнать предыдущий снимок без правки `Controller.kt` → `ShadowRef` сам читает манифест и дерево последней
  записи своего индекса (один `ls-tree`, после первого коммита экземпляра — память) → контракт вызова не меняется →
  альтернатива: хранить карту дайджест→объект в индексе ссылки (меняет формат файла состояния).
- Где брать ожидаемый git-id для проверки → из чтения захвата (`ContentCache` уже умеет `objectIds`); если захват его не
  посчитал (попадание D-364 без id) — из recovery-блоба (считается в `blobsRead`) → проверка I-12 сохраняется всегда.
- Перепроверка D-274 после одного чтения → сравнивает наблюдение файла (размер, mtime, ключ, ctime) с наблюдением до
  чтения и перечитывает изменившиеся; запись в пределах одного тика времени после чтения не видна (как и раньше для
  не-racy файлов), но манифест и штамп описывают одни и те же байты, а общий кэш racy-чтение не хранит → следующий захват
  прочитает файл заново. Безопасная альтернатива: перечитывать в перепроверке файлы, прочитанные в racy-окне.
- Нечитаемый файл → исключение `UnreadableInput` (типизированное, с путём), а не запись в `StampReport.unreadable`:
  штамп с неизвестным членом нельзя сравнивать с квитанциями без смены кодировки идентичности → безопасная альтернатива
  отсутствует без решения владельца.
- Счётчик чтений блобов → отдельные поля события (а не в `bytesRead`): дерево и хранилище различимы; страж WF-2
  суммирует их.
- Фикстура: `devtools/` получает mtime на час в прошлом. Свежесозданные файлы попадают в racy-окно D-364, и несвежий
  штамп открытия (`Controller.kt:675`, вне захвата) их перечитывает — это верное поведение, но счётчик зависел бы от того,
  как быстро сценарий идёт за генерацией (+114…+126 чтений и повтор 20-МБ файла при 300 в двух прогонах из четырёх).
  Реальный каталог инструментов старый. Первая гипотеза (антивирус) отвергнута трассировкой.
