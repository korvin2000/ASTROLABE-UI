## Цель
Пользователь задаёт на задачу жёсткие лимиты — деньги, минуты, запросы — и harness их **исполняет**: останавливается
до превышения, оставив резерв на проверку и отчёт, и честно отдаёт лучший проверенный результат. Профиль задаёт
вектор параметров при старте.

## Что сделать
1. **Лимиты на задачу** (публичный API старта кампании + Java-форма; `null` = без лимита; единицы в именах): деньги
   (по оплаченной сумме, при её отсутствии — по оценке; какая использована — видно в событии), минуты (инжектируемый
   `Clock`, не wall-clock напрямую), запросы (вызовы модели). Сейчас есть только `maxCells` и токенный бюджет.
2. **Принудительное исполнение** в контроллере: перед каждым вызовом модели остаток сравнивается с **резервом на
   проверку и отчёт** (правило резерва — явная чистая функция с тестами; описать в отчёте формулу: её проверит Codex).
   При достижении: контрольная точка → **лучший проверенный кандидат** (по тем же проверкам, что и обычная приёмка;
   рабочее дерево пользователя не подменяется — кандидат называется в итоге) → честный частичный результат
   (`PartialReason` для лимита — использовать существующий словарь, если подходит) с классом происхождения C2.
3. **Поднять лимит может только пользователь** (хост), регулятор и модель — никогда. После поднятия resume
   продолжает ту же попытку. В C3 лимиты читаются при старте и resume; смена «с границы хода» — E2, не здесь.
4. **Статические профили** «Экономный / Сбалансированный / Тщательный»: три пресета-вектора (effort по классу
   модели: дешёвая → high, дорогая → medium; глубина проверки; бюджеты результатов; предел контекста ниже ценового
   яруса; порог стоп-лосса — только значение для тени E4), выбор при старте задачи, заморожен на попытку
   (ярус 1 инварианта 12). Потолок замедления: ни один профиль не даёт > 2× (мягко) и ≥ 3× (жёстко) относительно
   «Сбалансированного» по числу запросов/времени — выразить проверяемым тестом на таблице профилей.
   Значение по умолчанию — «Сбалансированный» = текущие `Defaults` (поведение без выбора профиля не меняется).
5. **Видимость для хоста** (нужна C4: живой счётчик деньги / время / запросы / контекст): проверить, что события
   уже несут нужное (D-378), и добавить недостающее (расход против лимита, событие «лимит достигнут»).
6. Учесть инвариант 10 (бюджет) и идемпотентность resume (D-392): повторное открытие не списывает лимит дважды.
