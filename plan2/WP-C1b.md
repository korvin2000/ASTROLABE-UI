свидетельств.

## Что сделать
1. **Красная необязательная проверка записывается runtime.** Необязательная проверка (объявленная не-mandatory или
   `CHK-model-*`) завершилась красной → harness сам фиксирует «известно красная с квитанции #N» там, где сейчас от
   модели ждут Open-заметку; запись исчезает, когда та же проверка позеленела на текущем дереве. Обязательные проверки
   не затрагиваются (красная обязательная = rework, как сейчас). Отправная точка — KDoc «The one acceptance rule»
   (§8.7, D-337) в `K/verify/Resolution.kt` и exit-гейт. Ссылка плана `Resolution.kt:371-377` устарела после C2 — найти
   актуальное место самим.
2. **Подсказка достаточности — один раз.** Объявленные проверки зелёные на текущем дереве и обязательства закрыты →
   harness один раз (за ячейку; решение записать) подсказывает, что свидетельств достаточно и можно завершать. Канал —
   существующие подсказки (`K/cell/Gates.kt`), без нового блока; байты кэшируемого префикса `[S]` не меняются.
3. **Решение владельца 2026-10-03 (открытый вопрос D-396):** одобрение только судьёй review-ячейки **не** считается
   «проверено независимо». Судья (модель) класс происхождения не повышает: `independent` дают только объявленные
   проверки, прошедшие на финальном дереве; снятие test-integrity-заражения судьёй разрешает завершение, как сейчас, но
   затронутые run-элементы остаются свидетельством агента (класс не выше `agent_test`); `independent` возвращает
   только одобрение человека (`IntegrityApproval.Human`). `verifiedBy` остаётся в квитанции — по нему Studio (C4)
   покажет «одобрено судьёй-моделью». Решение о приёмке (можно ли завершить) **не меняется** — меняется только класс.
4. **Хвост C2:** проверка модели без `requirementIds` усиливает каждое требование. Выбрать и обосновать в отчёте:
   оставить (с записью решения) либо сузить (например, не усиливать требования, у которых есть собственные
   объявленные проверки). Безопасный вариант — тот, что не завышает класс.
5. **Хвост C1a:** живой фоновый handle во время stop-верификации невидим для `Scheduler.exclusive`. Исследовать;
   если исправление локальное (≈ ≤ 100 строк в `verify/Scheduler.kt` / `tool/run`) — исправить с тестом; иначе —
   в «Хвосты» с конкретным предложением.
6. **Данные для карточки Studio «сделать `npm test` проверкой проекта»** (саму карточку делает C4): хост должен
   уметь прочитать проверки `Origin.Model` (команда, cwd, вид свидетельства, последний результат) из итоговой
   квитанции или события. Проверить, что `FinishReceipt`/`CheckRun.checkOrigin` это уже дают; добавить только
