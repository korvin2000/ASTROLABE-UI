## Цель
Сейчас `eval-live/src/main/kotlin/io/astrolabe/evallive/StudioAttempt.kt` копирует политику Studio и расходится с ней
(12 ячеек и бюджет в 12 окон против 48 ячеек в Studio). Нужен один источник описания запуска в ядре, который читают и
`eval-live`, и мост Studio (Studio зависит от ядра, не наоборот).

## Что сделать
1. **`RunSpec` в ядре** (публичный API, `explicitApi`, записи `data class`, Java-форма где нужна): `Config`, политика
   кампании, модель ячейки, число ячеек, бюджет, лимиты задачи, флаги, пороги формы — всё, из чего собирается запуск.
   Умолчания — те, с которыми сегодня запускает Studio (источник: `ASTROUI/backend/bridge/.../StudioHost.kt`,
   `ASTROUI/backend/server/.../tasks/TaskService.java` — только читать; значения сверить с `K/Defaults.kt`).
   Одна фабрика умолчаний; никаких вторых копий чисел.
2. **`eval-live` читает `RunSpec`**: `StudioAttempt.kt` перестаёт копировать политику; плечо по умолчанию = умолчание
   `RunSpec`. Формат результата и CLI не ломать (B5 добавит `--arm` поверх).
3. **Runner для длинных сценариев:** (а) репозиторий без базового коммита; (б) сообщение пользователя посреди работы;
   (в) закрытие и повторное открытие той же работы и того же store (сейчас продолжение создаёт новый `WorkId`).
4. **Шаг Studio не делать** (корневой репозиторий, отдельная линия после слияния): в отчёте, раздел «Для шага Studio»,
   — точные места моста и сервера, которые должны перейти на `RunSpec`, и какой вызов ядра использовать.
