## 0. Главное на одной странице

1. **После фазы 0 reviewer больше не съедает токены.** На 34 живых прогонах после фазы 0 (1,71 млн токенов) review pass — 1,7 % токенов. Ваше ощущение «review уходит больше половины» было верным до фазы 0, но платили тогда не за review, а за цикл «нет вердикта → отказ → Continue»: сами вызовы review падали с нулём токенов.
2. **Главный расход сейчас — ритуал STATE.** 38 % токенов и 37 % ходов — ходы, в которых модель только ведёт регистр (план, заметки, `next`). Ещё 8 % — ходы с ошибкой схемы, в которых ничего не исполнилось. Единица стоимости — ход: каждый вызов заново отправляет около 5,4 тыс. токенов контекста, вывод — около 3 % токенов.
3. **«План на каждый запрос» создаёт не plan-cell.** Она не запускалась ни разу: все живые задачи шли в форме S0. План навязывают три текста и два гейта: заметка Studio «веди заметки через state», строки 7 и 14 kernel, обязанность роли; гейт Entry (сработал в 32 задачах из 34) и гейт Stall (36 срабатываний на 34 задачи), который считает прогрессом только записи в STATE, но не правки и не запуски.
4. **Review остался блокирующим шагом, но дешёвым.** Studio дописывает критерий «The change fulfils the request» в каждую задачу без тестов, и его вправе оценить только review pass — один вызов той же модели без инструментов. Из 40 живых вызовов: 34 approve, 6 «не могу проверить», 0 revise. То есть сейчас он почти ничего не ловит и почти ничего не стоит; его цена — задержка и лишняя остановка.
5. **Идей в архитектуре не не хватает — не хватает пропорциональности.** По карте `ideas/_map` из 181 идеи корпуса 111 уже есть в спецификации, 46 частично, 3 отсутствуют. Боль идёт от тяжёлых механизмов, включённых по умолчанию. Поэтому план — в основном вычитание и перекоммутация, а не новые подсистемы.
6. **Пять шагов с лучшим отношением эффекта к цене** (подробно — §7):
   - измерение в репозитории: разбивка токенов по назначению и сценарный прогон ×3 (иначе ни один выигрыш не доказать: разброс между прогонами — до 3×);
   - `prompt_cache_key` на кампанию для пути ChatGPT/Codex: кэш-попаданий 27 % против 78 % у OpenRouter;
   - пакет «S0 без ритуала»: Entry молчит при готовой приёмке, Stall считает правки и квитанции, тексты делают заметки необязательными, открытый шаг плана не блокирует сдачу;
   - пакет «трение инструментов»: описания параметров, бюджеты чтения, противоречие про shell, проверка синтаксиса;
   - review по риску в Studio: пропуск для мелких правок с честным ярлыком, заметки reviewer видны в UI, кнопка «Проверить сейчас».
7. **Главная оговорка.** Все измерения после фазы 0 сделаны на двух дешёвых моделях (`gpt-6-luna`, `glm-5.3-flash`) на низком effort, по одному прогону на ячейку, в почти пустых песочницах. Формы S1–S3, реальные репозитории с тестами и фронтирные модели вживую не наблюдались. «Меньше подпорок для умных моделей» — пока гипотеза; сокращение заметок Studio уже один раз ухудшило GLM с 6–9 до 16–17 вызовов. Каждое вычитание надо включать по классу модели и подтверждать тремя повторами.

## 3. Откуда берётся «план на каждый запрос»

Ядро плана не требует: ячейка S0, которая ни разу не писала STATE, может завершиться — выходной гейт блокирует только по *открытым* шагам. План навязывают пять мест:

| # | Источник | Где | Что делает |
|---|---|---|---|
| 1 | Заметка Studio | `ASTROUI/backend/bridge/.../Guidance.kt:14` | «Otherwise keep your notes with the state tool» плюс пример `plan.add`/`plan.tick` — в каждой задаче |
| 2 | Kernel, строки 7 и 14 | `cell/Layout.kt:49-51, 66-67` | «update STATE with typed ops» |
| 3 | Обязанность роли | `cell/Role.kt:84` | «maintain STATE through typed ops» |
| 4 | Гейт Entry | `cell/Gates.kt:314-329` | на первой правке подсказывает «no plan step carries an accept:», даже когда приёмка уже записана в контракте |
| 5 | Гейт Stall | `cell/Gates.kt:51-76, 363-378` | прогрессом считает только события STATE и зелёный приёмочный запуск; правки и запуски — не прогресс; срабатывает через 3 хода |

Дальше работает ловушка:
- Модель, послушав подсказку Entry, записывает шаг плана.
- Каждый открытый шаг при сдаче — пробел, требующий доработки (`verify/Resolution.kt:376-378`).
- В задачах Studio без тестов приёмка — один пункт `check:`. Он не может «позеленеть» запуском, поэтому у Stall вообще нет другого источника прогресса, кроме записей в STATE. Отсюда срабатывание почти в каждой задаче.

Самая наглядная трасса: Luna, hello world, раунд 2 — 17 вызовов и 76 тыс. токенов; «готово» отклонено только потому, что собственный шаг плана модели остался без отметки.

Отдельно — формы S1+, которых вы вживую ещё не видели:
- Plan-cell в S1/S2 запускается безусловно (`campaign/Controller.kt:727-736`).
- Размер задачи считается «наоборот»: `filesEstimated` — это транзитивные импортёры названных файлов плюс три файла-«хаба» (`ImpactPrescan.kt:72-77, 102`). Точный запрос с именем символа получает S1 и plan-cell, расплывчатый — S0. В монорепозитории с двумя наборами тестов S1 получает любой запрос, включая вопрос.
- Финиш S1 гоняет полный набор тестов, причём дважды одну и ту же команду (`CHK-full` и приёмочный пункт `AC-n` зарегистрированы с одинаковой командой, `verify/Check.kt:377-379`).

На реальном репозитории вроде самого ASTROLABE это и будет «план плюс 40 минут тестов на мелкую правку».

## 4. Где на самом деле стоит review

| Точка | Когда срабатывает | Кто проверяет | Активна в Studio сегодня |
|---|---|---|---|
| A. В ячейке, при каждом предложении завершения | есть пункт `check:`/`review:` или флаг test-integrity | `check:` → хост (Studio ReviewPass); только флаг → review-cell ядра | да, на каждой задаче без тестов |
| B. После ячейки | форма S2+, один из пяти триггеров (`delegate/Judge.kt:55-71`) | review-cell с инструментами, 12 ходов / 30 тыс. | нет: контракты Studio остаются S0 |
| C. Конец кампании | S2+ с ≥3 increments, refactor, неподписанный `review:` | review-cell, 60 тыс. | нет |
| D. Интеграция S3 | параллельные writers | review-cell | нет (S3 выключен) |
| E. По просьбе модели | `verify(review)` | — | редко |

Выводы:
- **Reviewer ядра уже с инструментами и уже по триггерам.** Без инструментов и безусловно работает только ReviewPass в Studio — потому что пункты `check:` всегда уходят хосту.
- **Корень безусловного review — правило D-50.** Код возврата 0 без счётчиков тестов не считается свидетельством (`verify/Scheduler.kt:217-219`). Сборка, typecheck и lint поэтому остаются «подсказками», и Studio вынуждена добавлять LLM-критерий.
- **Что ещё блокирует после фазы 0:** исполненный красный тест; открытый шаг плана; красная необязательная проверка без пункта Open с её id; замечание reviewer уровня major с указанием места — *любого* вида, включая Quality (`verify/Resolution.kt:246`). Архитектурная рубрика вкладывается в каждый пакет increment (`Controller.kt:2064`), то есть замечание о стиле может вернуть работу.
- **Дефект UI:** «не могу проверить» показывается как «Review pass: not yet» с красным узлом Flow, а сохранённые заметки reviewer не показываются вовсе (`timeline.ts:474`, `flow-model.ts:293-294`). Пока это не исправлено, «рекомендательный review» означал бы «выброшенный».
- **Пути B–D ни разу не исполнялись вживую.** Менять их вслепую рискованно; их доработка стоит ниже в ranking.

## 5. Идеи из `ideas/`: что брать

Моё мнение о корпусе в целом: четыре документа из пяти тянут в сторону «ещё больше проверок» (m-01…m-07: мутации, дифференциальный оракул, фальсификатор, скрытые тесты). Они исходят из формулы P(верно | принято) и снижают долю ложных приёмок. Для вашей системы и умных моделей приоритет обратный: измеренная проблема — избыточная проверка и налог протокола, а не ложная приёмка. При p = 0,9 большинство возвратов на доработку от reviewer — ложные тревоги.

## 6. Что делает индустрия в 2026 году

Коротко; источники — приложение B. Пометки: *изм.* — измерение, *заявл.* — заявление вендора, *втор.* — вторичный источник.

**Планирование.**
- Ни один ведущий harness не навязывает план на запрос. Codex CLI в версии 0.152.0 (2026-09-01) выключил инструмент планирования по умолчанию; Claude Code на фронтирных моделях убрал todo-инструменты (*втор.*); Amp убрал TODO-список.
- Документация Claude Code: «если дифф описывается одним предложением — пропусти план». Руководство Codex: не планировать «самые простые 25 %» задач.
- Исследование 176 конфигураций (arXiv 2609.20804, *изм.*): лёгкий план удваивает успех слабой модели (13,6 → 25,2 %), а сильной почти не меняет точность (68,6 против 69,0 %), только снижает стоимость.
- Плохой план хуже отсутствия плана (arXiv 2604.12147, *изм.*).

**Review.**
- У лидеров review рекомендательный: проверка Claude Code Review никогда не блокирует merge; Codex помечает только P0/P1; Amp зовёт «оракула» по требованию.
- Польза сосредоточена в больших диффах: находки в 84 % PR больше 1000 строк и в 31 % PR меньше 50 строк (Anthropic, *заявл.*).
- Reviewer с доступом к репозиторию и запуску точнее одноразового по диффу: 75–89 % против 60–75 % (arXiv 2607.06065, *изм.*). Studio сейчас использует худший вариант.
- LLM-судья плохо ловит ложное «готово»: AUROC не выше 0,65; простые детерминированные признаки дают 0,83–0,95 (arXiv 2606.09863, *изм.*).
- Meta автоматически одобряет около 60 % диффов по оценке риска без ухудшения показателей (arXiv 2605.30208, *изм.*).
- Anthropic о своём harness: оценщик «стоит своих денег, когда задача за пределами того, что модель надёжно делает сама»; с Opus 4.6 они убрали спринты и оставили один проход оценки в конце.

**Стоимость.**
- Harness меняет стоимость сильнее, чем результат: до 40× токенов на решённую задачу при разнице успеха 0–8 п.п. (arXiv 2607.22585, *изм.*, две модели среднего класса).
- Чтение из кэша стоит 0,025× входа на Fable 5.1 и 0,05× на Opus 5.5 (*заявл.*, прайс). Модель затрат в `docs/economics/costs.md:55` исходит из 0,1×.
- «Низкий effort, при неудаче повтор на высоком» дешевле и не хуже, чем всё на высоком: около 97 % за $0,17 против 95,3 % за $0,29 на задачу (Anthropic, *изм.*).

**Против интуиции «меньше проверок».**
- Около половины PR, проходящих тесты, мейнтейнеры не приняли бы (METR, 2026-03-10).
- Более сильные модели чаще подгоняют тесты: до 54–76 % на заведомо невыполнимых задачах; явная возможность сказать «задача невыполнима» снизила это с 54 % до 9 % (ImpossibleBench).
- Слабым моделям подпорки нужны.

## 10. Что должно остаться обязательным

- Исполненный красный тест блокирует; пользователь не может принять поверх красного.
- Код возврата 0 не называется «тесты прошли»; модель не может сама себе объявить демонстрацию свидетельством.
- Правки тестов, сборки и CI остаются триггером review.
- Контракт и приёмка вне полномочий модели; проверка фактов для исхода `answered`.
- Происхождение приёмки по каждому пункту (I7): «не проверялось» никогда не выдаётся за «проверено». Публикация выше стадии `patch` — только с проверенной приёмкой.
- Конечность круга доработки (I4, `maxFinalizations = 2`).
- Физика: защита от записи по устаревшему (CAS), покрытие показанных строк, снимки и откат, классы эффектов с одобрением, редактирование секретов, журнал эффектов.
- STATE на границах — перестройка контекста, продолжение, передача, возобновление, формы S1+: это единственная сводка, которая переносится между ячейками (модельных резюме нет).

## 11. Мои идеи поверх корпуса

Это мнение, не вывод из измерений.

1. **Harness наблюдает — модель не отчитывается.** Всё, что harness видит сам (дерево изменилось, запуск дал новый результат, приёмочный шаг позеленел), не должно требовать от модели записи. Модель пишет STATE только там, где знает то, чего harness не видит: гипотезу, решение, тупик. R3b и R3d — первый шаг; полный вариант — R15.
2. **Reviewer, который окупает себя.** Вести по каждому классу риска журнал: сколько стоил review, сколько замечаний, сколько из них привели к изменению. Порог пропуска подстраивается по этому журналу, а выборочный аудит (R17) даёт контроль. Такого первого класса нет ни у кого из лидеров; у Cursor Bugbot есть только обучаемые правила.
3. **Самоочищающийся harness.** Паспорт у каждого гейта (R14) превращает «меньше подпорок для умных моделей» из убеждения в решение по данным — по гейту и по классу модели, с перепроверкой на каждом релизе модели. Anthropic формулирует это так: каждый компонент harness кодирует предположение о том, чего модель не умеет.
4. **Каскад «effort → совет → модель».** При одной умной модели единственный настоящий рычаг — effort. Первая неудача: повтор на более высоком effort. Вторая: совет сильной модели одним вызовом (R16). Только потом смена модели. Сейчас «эскалация» в Studio — повтор той же модели.
5. **Честная лестница ярлыков как продуктовая черта.** Ответ → сделано → продемонстрировано → протестировано → проверено review → принято пользователем / политикой. Фаза 0 дала три ступени; R5 и R10 добавляют «не проверялось: низкий риск» и «продемонстрировано». Исследование arXiv 2609.20211 (по отчёту агента) показывает, почему статус должен идти структурой: когда пометка «не проверено» теряется при передаче, одобрение рискованных действий вырастает с 5 до 60 %.
6. **Детерминированный сторож вместо LLM-судьи на каждом финише.** Нет успешного запуска после последней правки, пустой дифф, правка тестов, упавшее число обнаруженных тестов — всё это harness считает бесплатно и точнее, чем судья.

**Про концепт в целом.** Ответ из `final_analyze.md` §11 остаётся в силе: слой фактов ценен, обязательная строгость — нет. Новое по сравнению с тем анализом:
- главный расход — не review, а ритуал STATE;
- причина ритуала — конкретные тексты и два гейта, которые чинятся за дни;
- для умных моделей самый дешёвый выигрыш — кэш и число ходов, а не сокращение промпта: при чтении из кэша по 0,025–0,05× цена kernel и схем пренебрежима.
